### 40자리 초과 SUM: to-be가 수학적 정답과 일치

Python 정수 연산으로 정확한 합을 구해 40자리에서 반올림한 값과 비교:

| | 값 (20k행 SUM(b)) |
|---|---|
| 수학적 정답 | 104686357802469135780246913577802.**4691340** |
| **to-be (on)** | 104686357802469135780246913577802.**4691340** ✓ |
| as-is (off) | 104686357802469135780246913577802.**4692299** ✗ (행당 반올림 드리프트) |

1M행에서도 동일 패턴: b의 소수부 0.8901234567 × 1,000,000 = 890123.4567 —
to-be는 정확히 …890123.**456700**, as-is는 …890123.**094750**으로 드리프트.

### 발견·수정한 버그 (본 구현 체크리스트에 반영됨)

해시 집계는 그룹 첫 튜플만 정렬로 보내고 부분합을 리스트로 저장했다가 acc->value에 로드 후 이어서
누적한다. 초기 POC는 로드된 부분합을 무시해 그룹 합이 "첫 값"이 되는 버그 발생 →
**"워드 누산기 비활성 + curr_cnt ≥ 1이면 acc->value를 먼저 시드"** 규칙으로 해결.

## 성능 1-b — 누적 경로 2차 최적화 (8/3, 커밋 `03c8e175f`→`20e610097`→`dc78c5fdc`)

perf annotate로 add_value 비용의 **32%가 `rep stos`(14워드 스테이징 memset)** 임을 확인 후:
① 계수를 스테이징 꼬리 3워드에 직접 로드(초기화 0바이트), 유효 워드만 더하고 캐리만 위로 전파,
used_words는 캐리 정지 위치로 O(1) 갱신 ② scale 확장은 정확한 필요 폭(`val_used + diff/19 + 1`)만,
부호 혼합은 윈도우 초과분만 초기화 ③ 캐리 아웃 시 ER_IT_DATA_OVERFLOW (`505cc63c3`).

| 쿼리 (1M행, 최솟값) | as-is | 1차 POC | **2차 최적화 후** |
|---|---|---|---|
| SUM(s) | 0.393s | 0.360s | **0.322s** (−18%) |
| SUM(b) | 0.451s | 0.319s | **0.281s** (**−38%**) |
| AVG(b) | 0.434s | 0.316s | **0.297s** (−32%) |

2차 후 add_value 내부: 호출 오버헤드 ~21% / 실제 덧셈 체인 ~25% / bswap 변환 ~9% —
memset·스캔 소멸, **누산 밴드는 바닥 도달** (남은 레버는 본구현의 헤더 인라인화 정도).
순수 SUM 쿼리에서도 이제 deform(12.4%)·인자 운반이 누적(3.2%)보다 큼 → 다음 이득은 후보 ①②.

## 성능 1-c — 레버 A1: 인자 운반 제거 (8/3, 커밋 `845911203`)

단일 피연산자 SUM/AVG(비-DISTINCT)는 인자를 즉시 소비하므로(첫 값은 value_to_accumulator
내부에서 딥카피, 이후 값은 읽기 전용), 행마다 하던 [std::vector 성장(malloc) → fetch_copy
딥카피 → 누적 → clear(free)]를 [fetch_peek → 누적]으로 축약. 게이트 on에서만 활성.

| 쿼리 | as-is | 누산기만 | **+A1** | as-is 대비 |
|---|---|---|---|---|
| SUM(s) 1M | 0.373s | 0.322s | **0.253s** | −32% |
| SUM(b) 1M | 0.457s | 0.281s | **0.224s** | **−51%** |
| AVG(b) 1M | 0.459s | 0.297s | **0.216s** | **−53%** |
| V1 (60M, 단순 SUM/AVG 5개) | 99.6s | 76.0s | **64.4s** | −35% |

- A1 단독 기여: 행·집계당 ~40~57ns (벡터 malloc/free + NUMERIC 딥카피 + clear의 실측 원가)
- 주의: 표에서 on의 SUM(s) > SUM(b)는 측정 순서 아티팩트 (SUM(s)가 항상 첫 쿼리 = 버퍼 풀 워밍업
  부담). 웜 상태 재측정 시 s 0.232 ≈ b 0.234 — 누산기는 자릿수(1~3워드)와 무관하게 행당 비용 동일.
  off/on 개선율 비교는 동일 순서 측정이라 유효
- 순수 누계 조각(V1−V0): as-is +65.3s → **+30.1s (−54%)**
- 정확성: A1은 값 경로만 바꾸므로 결과가 이전 on과 비트 단위 동일해야 하며, 실측 IDENTICAL
- 수식 SUM도 A1 대상(피연산자 = 수식 regu 1개)이지만 수식 파이프라인이 지배라 상대 효과 작음

### 1:1 대조 — 단순 SUM vs 수식 SUM (60M, A1 이전 빌드, 교차 2회 최솟값)

| 쿼리 | off | on(누산기만) |
|---|---|---|
| SUM(price) | 27.7s | 23.8s (−14%) |
| SUM(price×(1−disc)×(1+tax)) | 59.6s | 58.1s (−2.5%) |

수식 4연산(sub·mul·add·mul)이 +31s = **연산당 ~130ns** — perf 버킷·V2−V1 차등과 3중 수렴.
남은 최대 단일 조각 = 수식 파이프라인 → 레버 B1(one-word 연산자 fast path) 대상.

**로드맵 수정을 요구하는 발견**:
1. **수식 조각은 PG도 42.7s** — POC와 1.19x뿐. B2(융합)의 기대 이득 ~8s로 하향
   (numeric 곱셈 비용은 PG도 거의 그대로 지불)
2. **베이스가 2.2x (36.9 vs 17.0)** — NUMERIC 무관한 스캔+deform+그룹핑 격차 ~20s가
   잔여 격차(45.9s)의 최대 항목. 캠페인의 "deform은 공통 비용" 분류는 이 직렬 조건에선 성립 안 함
3. **누계 조각 2.8x (27.5 vs 9.7)** — 잔여 ~18s는 인자 fetch·dispatch·해시 운반
   → A3(행당 해시 메모리 델타 스킵)·A2(그룹키 캐시)의 대상
4. 잔여 격차 순위: 베이스 ~20s > 누계 운반 ~18s > 수식 ~8s — **B2보다 A계열·베이스가 우선**

### PG 대조 (상세: `pg_vs_cubrid.md`, TPCH-SSPQ FK 캠페인)

- 양쪽 6-way 병렬 동등 조건에서 wall 2.81x = **행당 명령어 수 2.95x** (IPC는 CUBRID 1.07x 우위) —
  격차는 스톨이 아니라 행당 일량
- 보고서 소스 대조표 1행(행당 완전 일반화 NUMERIC 연산자 vs PG accum_sum_add)이 정확히 본 POC가
  해결하는 항목; 2행(DB_VALUE 수명주기 churn ~10%)은 후보 ①(그룹키 fast path)의 대상
- 산수: 187 vs 68 CPU-s에서 누산기(−22) + 인자준비/그룹핑(−40) + 수식(−17) ⇒ ~108 CPU-s,
  **2.74x → ~1.6x**. 잔여는 표현식 해석·DB_VALUE 박싱 구조
- 스펙 논거 보강: PG numeric SUM이 정확 누적 + finalize 1회 정규화임을 소스 라인으로 확인
  (`numeric.c:4821 do_numeric_accum → accum_sum_add`) — 설계 문서의 "반올림 1회" 불변식과 동일 철학

## 확장 — 분석(analytic) SUM/AVG OVER (커밋 `f2c55cf3a`)

같은 워드 누산기를 `qdata_evaluate_analytic_func`(누적) / `qdata_finalize_analytic_func`(스냅샷)에
연결. 분석은 정렬 키 그룹마다 값을 **내보내면서 누적은 계속**되므로, finalize는 누산기를 파괴하지 않는
**비파괴 스냅샷**으로 처리 (설계 불변식 "반올림은 내보내는 시점의 스냅샷, 워드 상태로 역주입 금지" 그대로).

### 정확성

| 검증 항목 | 결과 |
|---|---|
| SUM/AVG OVER 매트릭스 (PARTITION/ORDER 조합, 20k) | off/on 완전 일치 |
| AVG 파티션 경계값 (part_value stash/reinstate 경로) | 1.42 / 1.92 / 2.42 / 499.92 정확 |
| 40자리 초과 러닝 SUM | to-be가 정답 (기존은 드리프트 — 아래 일관성) |

**일관성 확보 (이번 확장의 핵심 효과)**: 누계가 40자리를 넘는 데이터에서 기존에는
`SUM(x) OVER (ORDER BY …)` 마지막 행(118600)과 집계 `SUM(x)`(118700)가 **서로 달랐다**
(두 경로의 반올림 드리프트가 다르게 누적). to-be는 둘 다 118700(수학적 정답)으로 일치.

발견 버그 2건 (본 구현 체크리스트 반영): ① part_value 되돌림 직후 누적은 해시 집계의 "로드된
부분합"과 동일 상황 → 같은 시드 규칙으로 해결. ② `numeric_words_to_bytes`가 3워드 미만 윈도우에서
버퍼 아래를 읽음(스택 스냅샷에서 AVG가 2^128 가중치 쓰레기로 3.4e+38 출력) → 변환 윈도우
`MAX(win, 3)` 클램프로 해결.

### 성능 (t_claude_num 1M행, 교차 3회 최솟값, 외곽 MAX()로 출력 억제)

| 쿼리 | as-is | to-be | 개선 |
|---|---|---|---|
| SUM OVER (PARTITION BY mod10) — 스냅샷 10회 | 1.640s | 1.492s | **−9.0%** |
| SUM OVER (ORDER BY i) — 유니크 키, 스냅샷 100만 회 | 1.456s | 1.444s | −0.8% (≈노이즈) |
| SUM OVER (ORDER BY mod100) — 스냅샷 100회 | 1.516s | 1.379s | **−9.0%** |
| AVG OVER (PARTITION BY mod10 ORDER BY mod50) | 1.745s | 1.611s | **−7.7%** |

- 설계 예측 그대로 **스냅샷(emission) 횟수가 이득을 결정** — 행마다 스냅샷인 유니크 키 러닝 SUM이
  하한(±0)이고, 회귀는 없음. 스냅샷이 드문 파티션/동순위 케이스는 −8~9%
- 집계(−31%)보다 폭이 작은 이유: 분석 경로는 정렬·리스트파일 I/O·행당 emission 비용을 함께 지므로
  누적이 차지하는 비중 자체가 작음
- CUBRID는 window frame 절(ROWS BETWEEN 등)이 문법에 없음을 확인 — 무빙 프레임 고려 불필요

## 결론

1. **정확성**: 일반 케이스 완전 일치 + 40자리 초과 SUM은 수학적 정답과 일치 (기존은 드리프트),
   분석 확장으로 `SUM OVER 마지막 행 ≡ 집계 SUM` 일관성까지 확보
2. **성능**: 집계 SUM(b) −31%, AVG(b) −37%, TPC-H Q1 −12.7% (6천만 행), 누적 경로 자체는 5.6배 축소;
   분석 SUM/AVG OVER −8~9% (스냅샷 빈도가 하한 결정, 최악 케이스도 회귀 없음)
3. **설계 검증**: "5~7단계를 finalize로 미룬다"는 가설이 perf 분해로 그대로 확인됨
   (to-be 누적 경로에 나눗셈·자릿수·반올림·pack 심볼 부재)
4. 본 구현 시 추가 과제: 병렬 XASL 클론 경로, spill 불변식, 게이트 제거, QA answer 영향 합의
   — `design_numeric_sum_accumulator.md` 체크리스트 참조

## B2 — 집계 인자 수식의 워드 체인 융합 (8/4, 커밋 `8eedf29d5`)

수식 트리 {+,−,×}를 u128 체인값(계수·scale·부호·자릿수상한)으로 평가해 중간 DB_VALUE 없이
누산기에 직행. div/미지원 형태/38자리 초과 가능성은 행 단위 legacy 폴백 (비트 동일 보장 구조).

| 검증/측정 | 결과 |
|---|---|
| `SUM(price×(1−disc)×(1+tax))` 60M 직렬 | off 61.3s → **on 31.1s (−49%)** |
| 융합 결과 동일성 (20k `SUM(s*s)`, 60M q_expr) | **완전 일치** |
| 기존 매트릭스·t5 | IDENTICAL 유지 |
| Q1 (해시 GROUP BY) | **변화 없음 — 구조적 비대상** (아래) |

**기각 — 정수 직행 확장 (8/4)**: "SUM(BIGINT)가 행마다 NUMERIC 코어션을 낸다"는 전제로
INT/SHORT/BIGINT 값을 add_u128로 직행시키는 확장을 시도 → 실측 발동 0회. 원인:
누산 도메인 결정(`query_executor.c:21058`)이 정수 SUM은 **값 타입 그대로**(BIGINT는 BIGINT 누산)
쓰므로 NUMERIC 코어션 자체가 없음 — 대상 케이스 부재로 되돌림. 참고: 정수 SUM도 A1 peek의
수혜는 이미 받고 있음 (1M SUM(CAST(i AS BIGINT)) off 0.40 → on 0.33s).

핵심 발견 2건 (gdb 증거):
1. **1차 시도 효과 0의 원인**: 자릿수 가드를 선언 prec으로 계산 → fixed 컬럼 과대평가로 전행 폴백
   (`sum_charge` 상한 47>38). **실자릿수**(u128 clz+pow10 보정)로 교체해 해결 — "fixed의 prec은
   그릇 크기"라는 val_used 교훈의 재연
2. **적용 스코프는 플랜 종류가 가른다**: buildvalue(GROUP BY 없음)는 집계 인자가 TYPE_INARITH
   (트리 그대로) → 융합 ○. 해시 GROUP BY는 수식이 정렬/스필 튜플 컬럼용으로 출력 단계에서
   평가되고 인자는 TYPE_CONSTANT 참조 → 융합 대상 아님. **Q1의 수식 비용(~23% 버킷)의 실주인은
   튜플 디스크립터 단계** → 새 후보: 해시 적중 행(출력 불필요)의 수식 지연 평가

## 한계 / 참고

- POC 게이트(환경변수 CUBRID_NUMSUM_ACC)는 측정용이며 **본 구현에서 제거 확정** — 집계(및 2단계 분석) 내부 구현 방식일 뿐 사용자 가시 토글이 아니고, 파라미터로 남기면 '구식 반올림 호환 모드'를 영구 유지하는 비용(QA 매트릭스 2배)만 발생. 결과 변화는 이슈 합의 + QA answer 갱신으로 처리
- 병렬 스캔(XASL 클론) 경로는 POC 미검증 (conf `parallelism=0`) — 본 구현 체크리스트 6번
- spill 시 finalize 폴백(반올림 1회 추가)은 설계 문서의 불변식 논의 참조
- Q1 첫 로드 실패 이력: loaddb 날짜값은 따옴표 필수 (`'1992-01-02'`) — 미인용 시 산술식으로 토큰화되어 전행 실패
