## 1. 왜 하는가

| | 내용 |
|---|---|
| ① | **NUMERIC 덧셈 자체가 느렸다** — 별건으로 처리 (CBRD-27150, 일반 이항 연산자 최적화) |
| ② | **PG는 일반 이항 경로와 집계 누적 경로가 분리되어 있는데 CUBRID는 분리가 없다.** PG는 집계 시 `accum_sum_add`로 digit만 쌓고 정규화·저장형 변환을 그룹당 1회(`accum_sum_final`)만 한다. CUBRID는 집계가 **일반 이항 연산자를 행마다 호출**해서, 매 행 자릿수 계산·반올림 판정·17바이트 pack·DB_VALUE 재생성을 지불한다 |
| ③ | **그 결과 TPC-H Q1이 느리다** — 어느 구간이 얼마인지는 §2 |

즉 이 POC는 **CUBRID에 없던 "집계 전용 누적 경로"를 만드는 것**이다.

### 이항 연산자가 행마다 하는 일 (`float_numeric_db_value_add`의 단계 주석 그대로)

| 단계 | 집계에서 행마다 필요한가 |
|---|---|
| 1) 공통 precision/scale 계산 | scale 정렬 정보만 |
| 2) 작업 버퍼 크기 결정 | **불필요** — 누적기 크기는 고정 |
| 3) 계산 버퍼 초기화 + 절대값 패딩 | **불필요** |
| 4) scale 정렬 | 필요 |
| 5) 덧셈 | **필요 — 집계 누적에 실제로 필요한 것은 이것뿐** |
| 6) 결과 precision/scale 재계산 | **결과를 내보낼 때 1회면 충분** |
| 7) 반올림 + 17바이트 pack | 〃 |
| 8) DB_VALUE 저장 | 〃 |

집계는 중간 상태를 아무도 보지 않으므로 6·7·8은 그룹당 1회로 미룰 수 있는데, 행마다 지불하고 있었다.
perf 분해로 확인됨 — to-be의 누적 경로에는 **나눗셈·자릿수 계산·반올림·pack 심볼이 아예 없다**(as-is에서는 반올림 나눗셈 `__udivti3`가 누적 서브트리의 33.5%).
그리고 6·7·8을 미룬 결과가 §6의 "40자리 초과 SUM이 정답으로 바뀜"이다 — 행마다 반올림하지 않으므로 드리프트가 생기지 않는다.

## 2. TPC-H Q1 구간별 차이

같은 Q1을 세 단계로 잘라 차등 측정한다.

| 단계 | 쿼리 |
|---|---|
| **V0** | 스캔 + WHERE + GROUP BY + `COUNT(*)` — 집계 산술 없음 |
| **V1** | V0 + **단순 컬럼** 집계 5개 (`SUM/AVG(l_quantity)` 등) |
| **V2** | V1 + **집계 안에 수식**이 있는 것 2개 (`SUM(ep×(1−disc))`, `SUM(ep×(1−disc)×(1+tax))`) = 풀 Q1 |

**병렬 6워커, 데이터 버퍼 8G, 6,000만 행, 3회 최솟값** — 이 구간별 표는 **SA 모드**에서 잰 것이다.
CS 모드 전체 수치는 §5에 있고(as-is 30.56s → to-be 14.87s), 개선율은 두 모드가 사실상 같다.
구간별 재측정은 하지 않았다 — CS 모드 결함 조사에 시간을 썼고, 구간 비율이 달라질 이유가 없다.

| 구간 | as-is | **to-be** | 개선 | 이 구간의 비용 정체 |
|---|---|---|---|---|
| **V0** | 6.16s | 6.03s | — | 스캔·deform·해시 그룹핑 — **NUMERIC 무관** |
| **V1−V0** | +13.09s | **+5.71s** | **−56%** | 누적 그 자체 + 인자 운반 |
| **V2−V1** | +11.80s | **+3.34s** | **−72%** | 집계 안 수식의 연산·중간 DB_VALUE |
| **V2 = Q1** | **32.91s** | **15.03s** | **−54%** | |

PG(동일 장비, 병렬 6워커) **10.3s** → 격차 as-is 3.0x → **to-be 1.46x**

**읽는 법**: 개선분은 전부 V1·V2 구간에서 나왔고 V0은 그대로다. 즉 **NUMERIC 집계 경로만 바뀌었고 스캔·그룹핑은 손대지 않았다.** 남은 격차의 최대 항목은 V0의 PG 대비 2.2x(스캔·deform, NUMERIC 무관 영역)다.

## 3. NUMERIC 연산 함수의 종류와 역할

NUMERIC 연산자는 **소유 구간이 나뉘어 있다.** 이 POC는 그중 **집계 구간만** 확장하고
나머지는 손대지 않는다 — 어느 함수군이 무엇을 담당하는지 알고 나면 §4의 변경 내역이 읽힌다.

| 구간 | 담당 함수군 | 이 POC와의 관계 | 예시 |
|---|---|---|---|
| 단순·특수 (serial 등) | `numeric_db_value_*` | 그대로 — 워드 변환이 오히려 오버헤드다 | SELECT s.NEXT_VALUE |
| **일반 이항 연산** | `float_numeric_db_value_*` | **손대지 않음** — CBRD-27150이 최적화한 구간 | SELECT col1 + 3 |
| **집계·분석 누적** | 누계산(`numeric_sum_acc_*`) + 집계 내부식 혼합(`numeric_poc_chain_*`) | **이 POC가 신설·확장** | SELECT SUM(col1), AVG(col1), SUM(col1 * col2) |

### 누계산 내부의 3단 구조

누산기에 값을 넣는 경로는 입력 형식마다 하나씩이고, 산술은 하나로 모인다.

```
numeric_sum_acc_add_value (DB_VALUE *)   첫 값 → acc에 직접 세팅   ─┐
                                         이후  → 워드로 변환 ────────┤
                                                                     ├─→ numeric_sum_acc_add_core ()
numeric_sum_acc_add_u128 (uint128_t)     (첫 값 없음, assert)        │       스케일 정렬 후 방향만 고른다
   ← 워드 체인 결과                       워드로 변환 ───────────────┘         │
                                                          같은 부호 ──────────┤
                                                          다른 부호 ──────────┤
                                                                              ↓
                             float_numeric_add_acc ()            float_numeric_sub_acc ()
                             캐리 상위 전파 + 오버플로 검출        크기 비교 + 방향 결정 + 윈도우 재스캔
                             + 윈도우 O(1) 갱신                    + -0 방지
                                     │                                    │
                                     └──→ float_numeric_add () ←──────────┘ (float_numeric_sub ())
                                          임의 워드 수 범용, 인트린식, 캐리 반환 — 폴백 이항 연산과 공유
```

워드 덧셈 자체는 **기존 `float_numeric_add ()`/`float_numeric_sub ()`와 공유한다.** 원래 이 둘은
`uint128_t sum = a + b + carry; carry = sum >> 64` 방식이었고 캐리를 버렸는데(`void` 반환), 인트린식
(`_addcarry_u64`)으로 바꾸고 캐리를 반환하도록 했다. 폴백 호출자 6곳은 **이미 `(void)` 캐스트**여서
한 줄도 고치지 않았다.

두 방식은 같은 65비트 결과를 다른 그릇에 담을 뿐이다 — 인트린식은 `{반환값(CF 1비트), *out(64비트)}`,
uint128은 128비트 레지스터 쌍이고 상위 63비트는 **항상 0**이다. 그 낭비가 어셈블리에 드러난다
(가변 `n` 루프 기준 루프 본문 약 14개 명령 대 8개, uint128 쪽은 레지스터 4개를 push까지 한다).

같은 함수를 쓰면서도 **오버플로 처리는 호출자마다 다르다**:

| | 폴백 이항 연산 | 누산기 |
|---|---|---|
| 피연산자 | 2개 | **N개** (수백만 행) |
| 결과 상한 | 두 입력 precision으로 **계산 가능** | 계산 불가 |
| 버퍼 | `needed_bytes = MAX (lookup[result_prec], 17) + 1` → 워드 올림 | **14워드 고정** |
| 전략 | **넘칠 수 없게 만든다** → 반환값 무시 | **넘치면 잡는다** → `ER_IT_DATA_OVERFLOW` |

폴백 쪽 `+ 1` 바이트가 캐리 자릿수를 흡수하는 여유분인데 주석이 없다 — 없애면 조용히 깨지므로
이관 시 한 줄 달아둘 것.

**누산기 진입점 셋을 하나로 합치면 안 된다.** `add_core`의 계약은 주석 그대로 *활성 누산기에 더한다*이고,
첫 값은 더하기가 아니라 **세팅**이라 의미가 다르다. 게다가 `add_value`의 첫 값 경로는 스테이징
버퍼를 거치지 않고 `acc->words`로 **직접** 로드해 그룹당 복사 1회를 아낀다. 진입점별 변환
(`db_locate_numeric ()` vs u128 분해)은 입력 형식에 종속이라 애초에 `add_core`로 올릴 수 없다.

`add_u128`에는 첫 값 경로가 **없다** — 유일한 호출자가 `is_active`를 요구하므로 도달할 수
없었고(죽은 코드였다), 체인 결과에는 NUMERIC precision이 없어 `used_words`를 유도할 수도
없다. 그래서 `assert (acc->is_active)`로 계약만 남겼다. 결과적으로 **`is_active`를 켜는 곳은
`add_value` 하나뿐**이고, 이것이 워드 체인 분기가 타입 검사 없이 `is_active`만 보고도 안전한
근거다(§4).

**경계를 어떻게 지키는가** — 구분은 실행 시점에 결정된다. 집계 인자로만 소비되는 출력 수식을
쿼리 시작 시 1회 표시해 두고(`REGU_VARIABLE_AGG_OPERAND`), **표시된 것만** 혼합한다.
판정 근거는 *집계 인자가 그 수식이 쓴 DB_VALUE를 그대로 가리킨다*는 것이다(포인터 일치, gdb 실증).

경계가 지켜졌음은 측정으로 확인한다 — 순수 이항 연산(`WHERE v×w`, 300만 행)에서 곱셈을 2회
추가하는 비용이 **0.204s → 0.210s**로 사실상 동일하다.

한때 이 경계가 실제로 깨져 있었다 — `float_numeric_db_value_{add,sub,mul}`의 작업 버퍼
zero-fill을 게이트로 감싼 커밋(`ee323ece5`)이 있었고, 그래서 "순수 이항은 off와 동일"이라던
당시 측정(4.25s vs 4.08s, on이 더 빠름)은 **그 자신을 재고 있었다.** 되돌린 뒤의 위 수치가
경계의 근거다. 자세한 사유는 §4 기각 항목.

| ~~진입 조건에 결과 도메인 NUMERIC~~ | 비NUMERIC을 916 블록에서 걸러 peek 중복을 막으려 했다 | **기각 — `AVG` 전부 배제해 Q1 −18% 회귀. 막으려던 손해도 재현 안 됨** | 미커밋 (제거) |

### 각 항목 상세

#### 누계산 (워드 누산기)

집계는 중간 상태를 아무도 보지 않는다. 그런데 기존 경로는 일반 이항 연산자를 행마다 호출해
**결과 precision/scale 재계산 → 반올림 → 17바이트 pack → DB_VALUE 저장**을 매번 지불했다(§1의 6·7·8단계).
누계산은 값을 `uint64` 14워드(254자리)에 scale만 맞춰 더해 두고, 그룹이 끝날 때 한 번만
반올림·패킹한다. 40자리를 넘어도 계속 쌓기 때문에 **행마다 반올림하며 생기던 드리프트가 사라진다**
— §6의 "40자리 초과 SUM이 정답으로 바뀜"이 이것이다. 254자리를 넘으면 폴백이 아니라
`ER_IT_DATA_OVERFLOW`다.

#### 인자 peek

집계 인자를 읽을 때 `fetch_copy_dbval`은 DB_VALUE를 새로 만들어 값을 복사하고 나중에 해제한다.
누적은 값을 읽기만 하므로 `fetch_peek_dbval`로 **포인터만 받으면** 된다. 집계·분석 양쪽에 적용했고,
분석은 누산기가 이미 돌고 있을 때만 peek하고 첫 값·NULL·비NUMERIC은 기존 경로를 그대로 쓴다.

#### 직결 디스패치 / 워드 폭 산출

누계산이 활성인 동안에는 함수 종류(SUM/AVG/기타)를 다시 판정할 필요가 없어 분기를 건너뛴다.
워드 폭은 값의 상위 워드를 스캔해 구하던 것을, NUMERIC 헤더의 precision이 자릿수의 상한이라는
성질을 이용해 룩업 한 번으로 바꿨다.

#### 집계 내부식 혼합 (워드 체인)

`SUM(ep × (1 − disc) × (1 + tax))`처럼 집계 인자가 수식이면, 기존에는 연산마다 NUMERIC DB_VALUE를
만들고 버렸다. 혼합은 그 수식을 `{uint128 계수, scale, 부호}` 하나로 들고 다니며 `+`,`−`,`×`를
정수 연산으로 처리하고, **마지막에 DB_VALUE 하나만** 만든다. 중간 DB_VALUE가 0개가 된다.

어느 수식이 대상인지(적용 범위)는 §3에, 어떤 조건에서 폴백하는지는 아래 절에 있다.

#### 누계산 공유

`SUM(x)`와 `AVG(x)`가 같은 인자를 받으면 쌓는 합이 같다. 그래서 먼저 나온 쪽만 누적하고,
뒤쪽은 **값 확정(finalize) 시점에** 누산기 상태를 복사해 각자 마무리한다. AVG를 확정하면 합이
개수로 나뉘어 평균이 되므로, **복사는 반드시 확정 루프가 돌기 전에** 일어나야 한다.

**공유 관계 저장 규칙 — `shared_from`**

집계 노드마다 "내 누산을 앞선 몇 번째 집계와 공유하는가"를 정수 하나(`shared_from`)로 들고 있다.
규칙은 세 개다.

| | 규칙 |
|---|---|
| **초기화** | `0` = 공유 없음 (본인이 직접 누적) |
| **저장** | 공유할 앞선 집계의 인덱스 **+ 1** |
| **사용** | 값 **− 1** 로 되돌려 인덱스로 쓴다 |

Q1의 집계 8개에 실제로 담기는 값:

| # | 집계 | `shared_from` | 뜻 |
|---|---|---|---|
| 0 | `SUM(qty)` | `0` | 본인이 누적 |
| 1 | `SUM(ep)` | `0` | 〃 |
| 2 | `SUM(ep×(1−disc))` | `0` | 〃 |
| 3 | `SUM(ep×(1−disc)×(1+tax))` | `0` | 〃 |
| 4 | `AVG(qty)` | **`1`** | 0번 `SUM(qty)`의 누산을 공유 |
| 5 | `AVG(ep)` | **`2`** | 1번 `SUM(ep)`의 누산을 공유 |
| 6 | `AVG(disc)` | `0` | 같은 인자의 SUM이 없어 공유 상대가 없다 |
| 7 | `COUNT(*)` | `0` | 누계산 대상이 아니다 |

```c
agg_p->accumulator.shared_from = owner_index + 1;            /* 저장: +1 */
...
if (agg_p->accumulator.shared_from <= 0)  continue;          /* 0 = 공유 없음 */
owner_p = qdata_agg_node_at (agg_list, shared_from - 1);      /* 사용: −1 */
```

`<= 0`으로 음수까지 걸러내는 것은 **방어 코드**다. 정상 흐름에서 음수는 나올 수 없지만
배열 인덱스로 쓰는 값이므로 상한만이 아니라 하한도 검사한다(§9 4번).

**`0`을 "없음"으로 정한 이유**는 하나다 — 실행 전용 필드는 0으로 채워진 채 시작할 수 있고,
그 상태가 곧 "공유 없음"이면 초기화가 닿지 않은 경로에서도 오동작하지 않는다.
단 그 전제는 **스트림 경로에서 성립하지 않았다**(`stx_alloc_struct ()`는 memset을 하지 않는다 —
§9 함정 7). 그래서 최종 형태는 *`0` = 없음으로 두고, 스트림 복원 지점에서 명시적으로도 초기화한다*다.

#### 기각: 작업 버퍼 zero-fill 스킵 (`ee323ece5` 되돌림)

`float_numeric_db_value_{add,sub,mul}`은 VLA 작업 버퍼 3개를 `memset`으로 0으로 채운다. VLA 크기가
런타임 값이라 컴파일러가 인라인하지 못해 연산마다 실제 호출 3회가 된다 — 3워드 경로에서는 입력
버퍼를 어차피 전부 덮어쓰므로 결과 버퍼만 0으로 두면 된다는 것이 착안이었다.

**기각 사유 ① 경계 침범** — 이 세 함수는 **일반 이항 연산 구간**(§3)이고 CBRD-27150 소관이다.
"이 POC는 손대지 않는다"고 선언한 곳을 건드렸고, 그 결과 경계를 입증하던 측정("순수 이항은
off와 동일")이 자기 자신을 재는 상태가 됐다.

**기각 사유 ② 효과가 측정되지 않음** — 스캔이 산술을 덮지 않도록 컬럼 4개·300만 행 테이블에서
제거 전/후를 쟀다.

| 쿼리 | 제거 전 | 제거 후 |
|---|---|---|
| 곱셈 1회 (`WHERE v×w`) | 0.291s | 0.285s |
| 곱셈 3회 (`WHERE v×(1−w)×(1+v)`) | 0.495s | 0.495s |
| 분석 수식 | 2.720s | 2.529s |
| 분석 (수식 없음) | 2.590s | 2.319s |
| Q1 (집계) | 15.247s | 14.825s |

**이 함수를 아예 타지 않는 쿼리까지 모두 빨라졌다** — 서버 재시작이 수치를 0.2~0.4s 흔들기
때문이다. 그래서 서버 상태에 둔감한 지표, 곱셈 횟수만 다른 쌍으로 판정한다:
**곱셈 2회 추가 비용 0.204s(전) vs 0.210s(후)** — 구분되지 않는다.

즉 "효과가 없다"를 증명한 것은 아니고 **이 해상도로는 잡히지 않는다**는 뜻이다. 잃는 것이
측정되지 않으므로 되돌려 경계를 회복하는 편을 택했다.

**재도전 조건**: CBRD-27150 쪽에서, 쿼리가 아니라 **마이크로벤치로** 효과를 입증한 뒤 게이트 없이
적용한다. 0.006s 규모는 쿼리 측정으로 판정할 수 없다.

#### 분석 함수 확장

집계는 그룹이 끝날 때 한 번만 값을 내지만, 누적 분석 함수(`SUM(x) OVER (ORDER BY ...)`)는
**행마다 그때까지의 합**을 내보내고 계속 쌓아야 한다. 그래서 누산기를 끝내는 `finalize`와 별도로,
누산기를 그대로 남긴 채 값만 뽑는 `snapshot`을 두었다.

#### 서버 모드 결함 수정 (성능 아님 — 기능 복구)

**증상**: CS 모드(`csql -u dba <db>`)에서 NUMERIC 집계가 `Query execution failure #NNNNN`으로 실패했다.
게이트 on/off 모두, 직렬·병렬 모두. SA 모드에서는 정상이었다.

**원인**: 서버 모드는 클라이언트가 XASL을 **직렬화해 서버로 보내고**, 서버가
`stx_build_aggregate_type ()`으로 다시 만든다. 그런데 `stx_alloc_struct ()`는 `db_private_alloc`만
하고 **memset을 하지 않는다.** 스트림에 실려오지 않는 실행 전용 필드(`shared_from`, `num_sum_acc`)는
그 메모리에 있던 값을 그대로 갖게 되고, 쓰레기 인덱스로 owner를 찾지 못한 전파 코드가
**`er_set` 없이** `ER_FAILED`를 반환했다 — 그래서 에러 메시지가 저렇게 무의미했다.

**수정 세 가지** (`30305dcff`):

| | 내용 |
|---|---|
| 스트림 복원 지점 초기화 | `clear_value_at_clone_decache = false` 옆에서 `shared_from = 0`, `num_sum_acc.is_active = false`를 명시 |
| 전파를 게이트 안으로 | 게이트 off에서는 아무것도 링크되지 않으므로 전파 자체를 건너뛴다 (§9 함정 5의 재발이었다) |
| 실패에 에러 설정 | owner를 못 찾으면 `ER_QPROC_INVALID_XASLNODE` — 다음에는 진단이 가능하도록 |

**왜 여태 못 봤나**: SA 모드는 XASL을 메모리로 공유해 스트림 경로를 아예 타지 않는다.
POC 전체를 SA로만 측정·검증했기 때문에 드러나지 않았다. 자세한 경위는 §9 함정 7.

#### 기각: 해시 델타 스킵 (`5bec86046` 되돌림)

해시 집계는 스필 한도를 지키려고 행마다 누산기 메모리 증감을 다시 계산한다. 누산기 크기가
고정이면 그 증감은 항상 0이므로 건너뛰려 했다.

**기각 사유** — 판정 조건이 `pr_is_variable_type()`이었는데, CUBRID는 **NUMERIC을 가변 타입으로
분류**한다. 즉 NUMERIC 집계에서는 조건이 절대 성립하지 않아 **처음부터 한 번도 동작하지 않았다.**
그동안의 모든 성능 수치는 이 최적화 없이 나온 값이고, 되돌려도 회귀가 없다(병렬 Q1 14.7s 유지).

여기서 헷갈리기 쉬운 점: DB_VALUE 안의 NUMERIC은 `DB_NUMERIC_BUF_SIZE`(**17바이트**) **고정 버퍼**다.
그런데 회계에 쓰는 `pr_value_mem_size ()`는 그 버퍼 크기가 아니라 **값의 논리 크기**를 돌려준다 —
`mr_data_lengthval_numeric ()`이 `disk` 인자를 무시하고 float numeric은 precision 룩업,
fixed numeric은 유효 바이트 수로 계산한다. 그래서 값이 커지면 회계값도 커진다.
(부수적으로 알게 된 것: 해시 메모리 회계는 실제 점유(17바이트 고정)와 다른 값을 센다 — 기존 엔진
설계이고 POC 범위 밖이지만, 재도전 조건인 "도메인 상한 회계"가 더 타당해지는 근거다.)
조건을 "누계산 대상 SUM/AVG + COUNT"로 바꾸면 발동하지만, 폴백이 일어나면 `accumulator.value`가
갱신되어 증감이 0이라는 보장이 깨지고 **스필 회계가 부정확**해진다(결과는 맞지만 메모리 초과 위험).
안전하게 하려면 도메인 상한 기반 회계를 새로 도입해야 하는데, 효과는 워커 CPU 4.3%이고
**병렬 wall로는 노이즈에 묻혀 측정되지 않았다**(min 14.87 → 14.59s, median 동일).
효과 대비 위험·복잡도가 맞지 않아 전량 되돌렸다.

**재도전 조건**: 스필 회계를 "값 실측"에서 "도메인 상한"으로 바꾸는 작업과 함께. 그때는 폴백 여부와
무관하게 상한이 고정이므로 행마다 재계산할 이유가 사라진다.

#### 정수 피연산자 직결

체인은 `{+,−,×}` 트리만 융합하고, 그 셋이 아닌 노드를 만나면 **트리 전체를 거절**한다. 그런데
`n15 * id`는 파스 단계에서 `n15 * cast(id as numeric)`이 된다 — 타입 체킹이 `num + int → num`
규칙을 적용하는 방식이 **CAST 노드를 심는 것**이기 때문이다. 그래서 정수가 하나만 섞여도 체인이
통째로 죽었다. `SUM(price * qty)`는 이득을 못 받고 `SUM(ep * (1 - dc))`만 받고 있었다.

타입 결정은 컴파일 시점 1회지만 **변환은 런타임에 행마다** 일어난다. `id`가 디스크에 INT로 있는 한
누군가는 매 행 17바이트 NUMERIC을 만들어야 하고, 그게 저 캐스트 노드다. 그래서 논점은 캐스트를
없애는 것이 아니라 **얼마짜리 변환으로 바꾸느냐**였다.

| | 하는 일 |
|---|---|
| 레거시 | `fetch_peek_arith` 디스패치 → `numeric_coerce_int_to_num` → `arithptr->value`에 17바이트 패킹 |
| 정수 직결 | int64 읽어 128비트로 확장 |

**스케일 0의 근거가 도메인이 아니라는 점이 핵심이다.** `pt_coerce_expression_argument()`가 만드는
대상 도메인은 `(DB_DEFAULT_NUMERIC_PRECISION, DB_DEFAULT_NUMERIC_SCALE)` = (40, 0)인데, DB_VALUE
세계에서 precision 40은 **float numeric 표식**이라 실제 precision·scale은 값 헤더에 있다
(`db_get_numeric_scale()`가 그렇게 읽는다). 즉 도메인은 스케일을 보장하지 않는다. 보장하는 것은
**소스가 정수라는 사실**이다 — 캐스트가 헤더에 기록할 소수부가 애초에 없다. 그래서 정수를 스케일 0으로
싣는 것이 캐스트를 돌려 값을 읽는 것과 비트 단위로 같다.

안전장치는 세 겹이다.

| | 막는 것 |
|---|---|
| `T_CAST_WRAP`만 허용 | 명시적 `T_CAST`는 좁힐 수 있고, 건너뛰면 내야 할 오버플로 에러를 삼킨다 |
| 대상 도메인 == (40, 0) | `pt_eval_expr_type()`은 `PT_TYPE_MAYBE` 인자를 **상대 피연산자의 데이터 타입**으로 감싼다. `NUMERIC(15,2)`가 대상이면 정수를 두 자리 옮겨 놓는다 |
| 런타임 타입 재확인 | 도메인이 틀려도 오답이 아니라 폴백이 되도록 |

`T_CAST_WRAP`이 암시적 전용이라는 것은 코드로 확인했다. 이 opcode를 만드는 곳은
`xasl_generation.c:9307` 한 곳이고 조건은 `PT_EXPR_INFO_CAST_WRAP` 플래그인데, 그 플래그를 세우는
곳도 `type_checking.c:8546`(`pt_wrap_with_cast_op()`) 한 곳뿐이며 호출자는 전부 컴파일러 내부다.
문법 파일에는 이 플래그가 **0회** 등장한다.

측정은 6천만 행 TPC-H 모양 표(`ep NUMERIC(15,2) × ln INT`)에서, 캐스트가 없어 양쪽이 같은 코드를
도는 `ep * (1 - dc)`를 **대조군으로 끼워** 빌드 편향을 걷어냈다. 이 대조군이 한 배치에서 6% 차이를
보여 준 덕에 "ser이 6% 빨라졌다"는 헛된 결론을 막았다. 5회 교대 중앙값으로 직렬 5.9% · 병렬 5.0% ·
중첩 7.0%.

### 폴백 조건 — 두 종류로 나뉜다

**구조 조건 (쿼리 단위)** — 걸리면 그 수식은 처음부터 끝까지 혼합을 쓰지 않는다.

| 조건 | 예 |
|---|---|
| 집계 인자로 소비되는 수식이 아님 | `SELECT a*b`, `WHERE a*b > 0` |
| `+`, `−`, `×` 외의 연산이 트리에 섞임 | **나눗셈**, 함수 호출, CAST |
| 리프가 단순 값 참조가 아님 | 서브쿼리, 함수 결과 |
| 트리 깊이가 `max_recursion_sql_depth`에 근접 | 극히 깊은 수식 |
| 결과 도메인이 NULL 타입 | |
| 게이트 off | |

**값 조건 (행 단위)** — **행마다 독립적으로 판정**한다. 1행은 혼합, 2행은 폴백, 3행은 다시 혼합이 될 수 있다.

| 조건 | 언제 |
|---|---|
| 리프가 NULL | |
| 리프가 NUMERIC이 아님 | 정수·문자열이 섞인 수식 (`a*2`) |
| 리프 계수가 **128비트 초과** | 39자리를 넘는 값 |
| 중간·최종 계수가 128비트 오버플로 | 곱셈으로 커진 경우 |
| 곱셈 결과 scale > **252** | 레거시는 에러가 아니라 **반올림**해서 252로 맞춘다 — 체인이 재현 불가 |
| 곱셈 결과 scale < **−214** | 레거시는 **`ER_IT_DATA_OVERFLOW`**(WARNING) + 결과 NULL — 체인이 값을 내면 동작이 달라진다 |
| 두 항의 scale 차이가 38 초과 | 정렬에 `10^39` 이상이 필요 |

어느 쪽을 타도 **결과는 비트 단위로 같다.** 128비트에 들어가는 값은 최대 39자리이므로 기존 연산자가 반올림하는 경계(40자리)에 닿지 않기 때문이다. 즉 폴백은 **성능만** 되돌리고 답은 바꾸지 않는다 — Q1은 수식 값이 15자리 안쪽이라 사실상 전 행이 혼합을 탄다.

이득까지 함께 버린다.

**레거시와 동등함은 코드로 확인됐다.** 916 조건(SUM/AVG · 단일 인자 · `!DISTINCT` ·
`sort_list == NULL`)을 만족하는 집계가 레거시에서 거치는 분기는 전부 비켜간다 — NULL JSON
처리(1059)는 `else`의 `continue`로 우리 947행과 같고, DISTINCT/정렬(1104)은 916 조건이 이미
배제하며, `QPROC_IS_INTERPOLATION_FUNC`(1165, = MEDIAN/PERCENTILE_CONT/DISC)와
GROUP_CONCAT(1288)은 해당 없다. 남는 `else`(1317)가 부르는
`qdata_aggregate_multiple_values_to_accumulator ()`는 **인자가 1개면 첫 줄에서 곧바로**
`qdata_aggregate_value_to_accumulator (..., false)`로 넘긴다 — 우리가 965에서 부르는 것과 마지막
인자까지 같다. 즉 **차이는 copy → peek 하나뿐이고 건너뛰는 처리가 없다.**

**peek 포인터는 보관되지 않는다.** 첫 값은 `copy_operator` 경로(701행)에서 `pr_clone_value ()`
또는 `db_value_coerce ()`로 **복사**되고, 이후 값은 `qdata_add_dbval ()`이 **읽기만** 한다.
타입과 무관하게 안전하다.

**진입 조건은 `qdata_agg_is_plain_sum_avg ()`로 뺐다** — 이름이 곧 "여기는 SUM/AVG 전용
구간"이라는 선언이고, 본문은 `---- NUMERIC only ----` / `---- any type ----` 라벨로 두 층을
구분한다. 워드 체인 쪽(949행)에는 타입 검사가 없는데, `num_sum_acc.is_active`가 그 자리를
대신하기 때문이다 — 이 플래그를 켜는 곳은 `numeric_sum_acc_add_value ()` 하나뿐이고 그 호출은
전부 NUMERIC 검사 뒤에 있다. 순수 정수 수식은 첫 행에서 NUMERIC 검사를 통과하지 못해
`is_active`가 끝내 꺼진 채로 남고, 그래서 949행에 도달하지 못한다. 다만 이 플래그는 "이미
NUMERIC을 쌓았다"는 뜻이지 "이번 행이 NUMERIC"은 아니므로, peek 쪽(953행)의 값 타입 검사는
여전히 필요하다(수식·host 변수는 행마다 타입이 바뀔 수 있다).

`agg_p->flag.min_max_optimized`는 **조건에서 빼고 `assert`로 남겼다.** SUM/AVG가 이걸 가질 수
없는 이유가 3단이다 — ① `pt_optimize_min_max_list ()`는 `PT_MIN`/`PT_MAX`일 때만 호출되고
(`xasl_generation.c:4033`) ② 그 안에서도 `case PT_MIN:`/`case PT_MAX:`에서만 켜지며
(`:4621`, `:4632`) ③ `pt_set_access_spec_for_aggregation ()`은 min/max 전용 스캔이 아닌 집계가
하나라도 섞이면 **모든 집계의 플래그를 지운다**(`:4695`). 즉 `SELECT MIN(a), SUM(b)`에서는
MIN 쪽 플래그마저 꺼진다.

`AVG(int)`·`SUM(int)`는 300만 행에서 **`Overflow occurred in addition context`로 실패**해 측정에서
빠졌다(`SUM(g)`로 대체). AVG는 결과가 DOUBLE인데도 **누적은 입력 타입으로** 한다 — 결과
도메인이 내부 누적 타입을 알려주지 않는다는 ⑨의 근거를 하나 더 보탠다. POC 범위 밖.

### 40자리 초과 결과의 반올림은 정상 동작

`9999…9(40자리) + 9999…9`는 41자리가 되어 40자리로 반올림되므로 `(a+b)-b ≠ a`가 된다.
**Oracle도 동일한 결과**를 낸다(사용자 교차 확인) — 유효숫자 한계이지 결함이 아니다.
반올림은 `float_numeric_round_and_pack ()`이 담당하며 이 POC가 손대지 않은 코드다.
`a+a = a*2`처럼 양쪽이 같은 반올림을 겪는 항등식은 전부 위반 0이다.

### 해시 집계 엔트리 크기와 스필 시작점 — 게이트를 꺼도 남는 비용

`qdata_get_agg_hvalue_size()`가 `sizeof(aggregate_accumulator)`를 그대로 해시 예산
(`max_agg_hash_size`, 기본 2MB)에 더한다. 누산기를 구조체에 박았으므로 **게이트 OFF에서도** 엔트리가
커져 있다. develop 대비 회귀 여부를 재기 위해 `c27d4754c`를 별도 워크트리에 빌드해 대조했다.

계측으로 실비용을 직접 찍었다(`hash_size / group_count`, 임시 진단 후 제거).

| | 누산기 | 엔트리 실측 | 축출 시작 카디널리티 (2MB ÷ 엔트리) |
|---|---|---|---|
| base `c27d4754c` | 32 B | 140 B | 약 **15,000** 그룹 |
| POC | 168 B | **276 B** | 약 **7,600** 그룹 |

누산기가 엔트리의 61%를 차지한다. **엔트리가 두 배가 되고 스필 시작점이 절반으로 당겨진다.**
군집 배치 16,000 그룹에서 `hash_size`가 2,097,048로 예산에 붙고 8,402건이 축출되는 것을 실측했다.

**그런데 이것이 시간으로는 나타나지 않는다.** 회귀 구간(7.6K~15K) 한가운데인 10,000 그룹에서
base 1.211/1.409s vs POC-OFF 1.301/1.298s로 구분되지 않는다. 이 계획은 `sort: true`라 정렬을 어차피
하고, 축출된 항목을 partial 목록에 쓰는 비용이 200만 행 스캔에 비해 작기 때문이다. 게이트 ON은 오히려
같은 조건에서 20~30% 빠르다(스필하는 그룹바이에서도 누계산 이득이 축출 비용을 덮는다).

**본구현에서 줄이려면** `num_sum_acc`를 구조체에 박지 말고 필요할 때만 붙이는 방법이 있다. 그러면
OFF 비용이 8바이트로 줄고 NUMERIC SUM/AVG가 아닌 집계는 아예 물지 않는다. 다만
`qdata_aggregate_accumulator_to_accumulator()`의 구조체 대입이 포인터 대입으로 바뀌므로 수명 관리를
같이 손봐야 하고(이 POC에서 워커 병합 오답을 낸 바로 그 코드다), `qdata_get_agg_hvalue_size()`도 그
할당을 세도록 고쳐야 한다.

| 잘못 고른 신호 | 실제 의미 |
|---|---|
| 트레이스의 `hash: partial` | 메모리 스필이 아니라 **선택도 휴리스틱이 해시를 포기**했다는 뜻(`HASH_AGGREGATE_VH_SELECTIVITY_*`, 튜플 2000·선택도 0.5). 예산 초과로 LRU를 쫓아내는 루프는 `state`를 건드리지 않는다 |
| 트레이스의 `page` | `PSTAT_SORT_NUM_DATA_PAGES` 델타 — **정렬 페이지**다. 예산을 32K↔128M으로 4000배 바꿔도 값이 동일했다 |

추가로 두 가지가 실험을 무력화했다.

- **자동 병렬 스캔**: `px_scan_result_handler`가 `groupby_hash`를 `HS_REJECT_ALL`로 덮어써 항상
  `partial`로 보인다(주석에 명시). `max_parallel_workers=0` 필요 — `PARALLEL(1)` 힌트로는 안 꺼진다.
- **`MOD(ROWNUM, k)` 데이터**: 첫 k행이 전부 다른 그룹이라 튜플 2000 시점 선택도가 1.0이고,
  k > 1000이면 무조건 해시를 포기한다. 반대로 완전 군집 배치는 입력이 정렬 상태가 되어 해시를 안 쓴다.

결론적으로 **스필을 관찰하려 하지 말고 엔트리 비용을 재서 나눗셈하는 편이 빠르고 정확했다.**

4. **결과 변화 합의** — 40자리 초과 SUM이 정답으로 바뀜 → 스펙 합의 + QA answer 갱신

## 9. 환경 · 함정

- 병렬은 `/*+ PARALLEL(n) */` 힌트 필수 (heap 자동 병렬 없음, `parallelism`은 동적 변경 불가)
- 벤치 DB를 **`demodb`에 두지 말 것** — 빌드가 초기화한다. `pocbench`(디스크) 사용
- 빌드/install이 `cubrid.conf`·`databases.txt`를 초기화 → 측정 전 복원 + **버퍼 크기 재확인**
- **`build.sh install`이 실행 트리를 갱신하지 않는다** — `build_x86_64_release/_install/CUBRID`에만
  설치되고 `$CUBRID`(`/home/cubrid/CUBRID`)는 그대로일 수 있다(로그가 전부 `Up-to-date`, exit=0).
  `cp -a _install/CUBRID/bin/. $CUBRID/bin/` + 같은 식으로 `lib/`를 복사한다(conf는 제외).
  **검증 전에 `ls -l $CUBRID/bin/cub_server`로 타임스탬프를 확인할 것** — 이걸 놓쳐서 진단 로그를
  넣은 빌드 2회가 반영되지 않았고, "로그가 안 찍힌다 → 이 경로가 원인이 아니다"라는 잘못된
  추론을 두 번 했다
- 데이터 버퍼 512M ↔ 8G는 Q1에 무영향
- `cubrid server start`를 파이프에 물리면 데몬이 FD를 상속해 블록 → `>/dev/null`
- loaddb 날짜값은 따옴표 필수 (`'1992-01-02'`)
- **프로파일의 CPU %를 wall 개선으로 착각하지 말 것** — 6워커 병렬에서 워커 CPU 합은 wall의 약 5.8배다.
  즉 **CPU 1s 절감 ≈ wall 0.17s**. 병렬 Q1의 측정 노이즈가 ±1.5s이므로 **CPU 4% 미만의 개선은 병렬 wall로
  검증할 수 없다** — 그런 항목은 `PARALLEL` 힌트를 뺀 직렬로 재야 CPU 절감이 1:1로 드러난다

### 집계 코드를 건드릴 때 (이번에 값비싸게 배운 것)

집계는 경로가 **직렬 / 병렬 / 해시 / 정렬 / buildvalue**로 갈리고, 집계 리스트도 3중이다:

```
xasl->proc.buildlist.g_agg_list   원본 — 쿼리 시작 시 준비
gbstate->g_dim[N].d_agg_list      GROUP BY 차원별 — finalize가 이걸 쓴다
value->accumulators[]             해시 그룹별 배열 — 위 둘을 잇는다
```

누적 루틴은 **2개**이고, 갈리는 기준은 직렬/병렬이 아니라 **BUILDVALUE인가 아닌가**다:

| 누적 루틴 | 호출 지점 | 담당 |
|---|---|---|
| `qdata_evaluate_aggregate_list ()` | `query_executor.c:1322` (`qexec_end_one_iteration`) | **직렬** BUILDVALUE (GROUP BY 없음) |
| 〃 | `query_executor.c:4597` / `:4791` | GROUP BY — 정렬 기반 / 해시. **직렬·병렬 공용** |
| `px_scan_result_handler::accumulate_node ()` | 워커 전용 | **병렬** BUILDVALUE |

**`qdata_evaluate_aggregate_list ()`는 직렬 전용이 아니다.** 병렬 BUILDLIST 워커도 GROUP BY
집계에서 이걸 쓴다 — Q1(`PARALLEL(6)`) 워커 프로파일에 이 함수 6.35%와
`qexec_hash_gby_agg_tuple` 4.26%가 함께 잡히고, 여기에 넣은 조건 하나가 Q1을 17.59s로
만들었다(⑨). 갈라지는 것은 **병렬 BUILDVALUE 하나뿐**이고, 그건 자체 누적 루틴을 갖고 있어
`qdata_evaluate_aggregate_list ()`를 고쳐도 전혀 영향받지 않는다.

이 POC는 병렬 BUILDVALUE를 마지막까지 놓치고 있었다 — Q1(병렬 GROUP BY)과 분석만
프로파일했고 GROUP BY 없는 집계는 한 번도 확인하지 않았기 때문이다. **정확성 TC 101개로도
못 잡는다**: off/on 결과 비교는 "최적화가 아예 안 걸렸다"를 원리상 검출하지 못한다.
최적화 적용 여부는 **성능으로만** 검증된다.

분석(`OVER (...)`)은 `qdata_evaluate_analytic_func ()`로 또 따로 간다.

그래서 새 처리를 넣을 때 다음을 전부 확인해야 한다. 이번에 이 유형의 결함이 **8번** 나왔다.

1. **병렬 경로에도 넣었는가** — 워커는 자기 XASL을 쓰고, 도메인 해소조차 전용 함수(`..._for_parallel_heap_scan_g_agg`)가 따로 있다. 직렬 쪽만 고치면 병렬에서 조용히 무효가 된다.
   **교훈을 배운 뒤에는 이전 커밋도 소급 점검할 것** — 이 함정을 알기 전에 만든 `fixed_hvalue_size`(`5bec86046`)를
   다시 보지 않아서, 그것이 병렬에서 안 도는 줄 알고 하루 뒤에 고치려 했다. 실제 원인은 병렬이 아니라
   타입 분류였고(§4 기각 항목), 결국 전량 되돌렸다. **"쿼리당 1회 판정"을 새로 만들면 그 즉시 병렬 호출
   지점을 함께 만들고, 이미 만든 것들도 같은 눈으로 훑어야 한다.**
2. **값을 꺼내는 지점을 모두 찾았는가** — 최종 출력 / 해시 스필 / 부분합 병합
3. **새 필드의 센티넬이 `0`인가** — 실행 전용 필드는 직렬화되지 않아 0으로 채워지고, 초기화 함수가 모든 경로에서 호출된다는 보장이 없다. `-1`을 "없음"으로 쓰면 초기화 누락이 곧 오동작이 된다. 인덱스는 1-based로 저장해서 `0 = 없음`이 되게 한다
4. **음수·범위 방어** — 배열 인덱스로 쓰는 값은 상한만이 아니라 **하한도** 검사한다
5. **게이트 안에 있는가** — off에서 기존 동작이 100% 유지되어야 한다
6. **SA(직렬)로만 gdb 확인하지 말 것** — 병렬 특유 문제가 드러나지 않는다
7. **SA 모드로만 측정·검증하지 말 것** — 서버 모드(CS)는 클라이언트가 XASL을 **직렬화해서 서버로 보내고**, 서버는 `stx_build_aggregate_type ()`으로 다시 만든다. SA는 XASL을 메모리로 공유해 이 경로를 아예 타지 않는다
8. **집계의 `domain`으로 입력 타입을 거르지 말 것** — `aggregate_list_node::domain`은 주석 그대로 *domain of the **result***다. **`AVG`의 결과 도메인은 입력과 무관하게 항상 DOUBLE**이다(`func_type.cpp`의 `case PT_AVG:` → `arg_type = PT_TYPE_DOUBLE`). 입력 타입으로 거르려면 값의 런타임 타입(`DB_VALUE_DOMAIN_TYPE`)이나 operand의 도메인(`operands->value.domain`)을 봐야 한다. `accumulator_domain.value_dom`도 안 된다 — 실행 전 `NULL`이고 첫 값에서 결정된다(`query_executor.c:15932`, `20852`)
9. **기존 함수 한가운데 조기 반환을 넣을 때는 그 함수가 *끝에서* 하는 일을 확인할 것** — 아래 9번 상세 참조. **release 검증만으로는 절대 드러나지 않는다**
10. **기존 함수를 새로 호출할 때는 그 함수의 *전제*를 물려받는지 확인할 것** — 아래 10번 상세 참조. 우리는 "호출자가 버퍼 여유를 보장한다"는 전제 위에 서 있던 함수를 **고정 버퍼로** 불렀다
11. **상한 추정치를 거부 기준으로 쓰지 말 것** — 상한은 "이만큼이면 확실히 담긴다"이지 "이걸 넘으면 못 담는다"가 아니다. 판정은 실측값(캐리)으로 하고, 추정치는 클램프에만 쓴다

#### 7번이 실제로 터진 방식 (커밋 `30305dcff`)

`stx_alloc_struct ()`는 `db_private_alloc`만 하고 **memset을 하지 않는다.** 그래서 스트림에서
복원된 accumulator의 실행 전용 필드(`shared_from`, `num_sum_acc`)는 그 메모리에 있던 값을
그대로 갖는다. 즉 **3번의 "0으로 채워진다"는 전제가 스트림 XASL에서는 성립하지 않는다** —
`shared_from` 주석에 "스트림에서 온 XASL이 그 예"라고 적었던 것이 정확히 거꾸로였다.

쓰레기 인덱스로 `qdata_propagate_shared_accumulators ()`가 owner를 찾지 못하고,
`er_set` 없이 `ER_FAILED`를 반환해 `Query execution failure #NNNNN`이라는 진단 불가능한
메시지만 남았다. 게다가 그 함수는 **게이트 밖**에서 돌고 있었다(5번 재발).

증상이 게이트·집계 개수·통계 유무에 따라 성공/실패로 갈려 오래 헤맸다 — 초기화되지 않은
메모리의 전형이다. 수정은 `clear_value_at_clone_decache = false` 옆에 두 필드를 명시적으로
초기화하고, 전파를 게이트 안으로 옮기고, owner 실패에 에러를 설정하는 것이다.

**검증은 반드시 서버 모드(`csql -u dba <db>`)로 한다.** `csql -S`는 SA 모드다.
게이트는 환경변수 `CUBRID_NUMSUM_ACC=1`을 **서버 프로세스가** 가져야 켜지므로,
서버 모드 A/B는 `cubrid server stop` → 환경변수 설정/해제 → `start`로 전환한다
(`/proc/<cub_server pid>/environ`으로 실제 적용을 확인할 것).

#### 8번이 실제로 터진 방식 — 그리고 PG를 대조군으로 쓴 법

③(병렬 BUILDVALUE)을 고치면서, 정수 집계가 `fetch_peek_dbval ()`을 한 번 더 부르는
손해(`SUM(int)` 0.647 → 0.730)를 막으려고 ①의 진입 조건에 `TP_DOMAIN_TYPE (agg_p->domain)
== DB_TYPE_NUMERIC`을 넣었다. 정수는 실제로 걸러졌다 — **그리고 `AVG(numeric)`도 전부
걸러졌다.** 같은 줄에 있던 `agg_p->function == PT_AVG`는 그 순간 도달 불가능한 조건이 됐다.
Q1은 AVG를 3개 쓰므로 **14.87s → 17.59s로 되돌아갔다.**

원인 추적이 어려웠던 이유는 **환경이 함께 변해 있었기 때문**이다. 그날 t_an·t_vf 등을 만들고
서버를 수십 번 재시작한 뒤라, 절대값 비교가 오염돼 있었다. perf 프로파일에도 회귀 징후가
없었다(우리 심볼은 오히려 줄었고, 전체가 균일하게 늘어난 모양이었다) — 전형적인 "환경 탓"
그림이다.

**PG가 대조군이 됐다.** PG는 우리 코드와 무관하고, 같은 머신·같은 8G 버퍼·같은 6,000만 행에서
같은 Q1을 돈다. 머신 상태가 나빠졌다면 PG도 그만큼 느려져야 한다.

| | 이전 | 회귀 조사 시점 | 변화 |
|---|---|---|---|
| PG Q1 | 10.3s | 10.82s | **+5%** |
| CUBRID Q1 | 14.87s | 17.59s | **+18%** |

PG가 5%만 움직였으므로 18%는 환경으로 설명되지 않는다 — 이 한 번의 측정이 "환경 탓"을
기각하고 코드로 방향을 돌려줬다. 조건을 걷어내니 15.25s로, 환경 보정 기대치(14.87 × 1.05 =
15.61s)보다 오히려 빨랐다.

**교훈**: 성능 회귀를 절대값으로 판정하지 말 것. 같은 머신에서 도는 **무관한 대조군**(여기서는
PG, 없다면 게이트 OFF 빌드)을 같은 세션에서 함께 재면, 환경 변화와 코드 회귀를 분리할 수 있다.

#### 9번이 실제로 터진 방식 — debug 빌드에서만 죽는 결함

워드 체인은 `fetch_peek_arith ()` 한가운데에서 조기 반환한다.

```c
if (fetch_poc_eval_chain (thread_p, regu_var, vd, obj_oid, tpl, &chain_val))
  {
    numeric_poc_chain_to_dbv (&chain_val, arithptr->value);
    *peek_dbval = arithptr->value;
    return NO_ERROR;          /* ← 함수 끝의 상수성 판정을 건너뛴다 */
  }
```

그런데 이 함수는 **끝에서 반드시** 피연산자들의 상수성을 종합해 `REGU_VARIABLE_FETCH_ALL_CONST`
또는 `..._NOT_CONST` 중 하나를 설정한다(`fetch.c:4027`). 호출자는 그것을 **사후조건으로 assert**
한다(`:4306`). 조기 반환은 그 계약을 깨뜨렸다.

```
csql: src/query/fetch.c:4307: fetch_peek_dbval_slow: Assertion
  `REGU_VARIABLE_IS_FLAGED (regu_var, REGU_VARIABLE_FETCH_ALL_CONST)
   || REGU_VARIABLE_IS_FLAGED (regu_var, REGU_VARIABLE_FETCH_NOT_CONST)' failed.
```

**release에서는 결과가 정확했다.** 플래그가 없으면 `ALL_CONST` 캐싱 경로를 타지 않아 매 행
재평가하기 때문이다 — 즉 **정확성은 무사했고 규약만 깨져 있었다.** 그래서 101개 TC, 530행,
`t_mix` 118줄, Q1이 전부 통과했다. debug 빌드에서는 그대로 **서버가 죽는다**(로그에 흔적도
남지 않는다 — assert는 stderr로 나가고 서버의 stderr는 버려진다).

수정은 조기 반환 전에 `NOT_CONST`를 설정하는 것이다. `ALL_CONST`를 붙이면 안 된다 — 집계
인자는 컬럼을 읽어 행마다 값이 바뀌는데, 그러면 다음 호출이 캐시된 `arithptr->value`를
재사용해 **결과가 틀어진다.**

**진단 요령**: 서버 stderr가 버려지므로 SA 모드(`csql -S`)로 재현하면 assert 메시지가 터미널에
그대로 나온다. 그리고 게이트 OFF로 같은 쿼리를 돌려 "우리 코드 탓인지"를 한 번에 가릴 수 있다.

**교훈**: 기존 함수 한가운데 조기 반환을 넣을 때는 **그 함수가 끝에서 하는 일**(플래그 설정,
카운터 갱신, 자원 반납)을 반드시 확인할 것. 그리고 **release만으로 검증을 끝내지 말 것** —
이 부류는 결과가 맞기 때문에 결과 비교로는 원리상 잡히지 않는다.

#### 10번·11번이 실제로 터진 방식 — 스케일 정렬이 자릿수를 조용히 버렸다

`numeric_sum_acc_add_core ()`는 스케일을 맞추려고 누산기에 `10^(스케일차)`를 곱한다. 그
곱셈을 하는 `float_numeric_mul_pow10 ()`은 **캐리를 `assert (carry == 0)`으로만 처리하고
버렸다** — 베이스 커밋부터 그랬고, 그때는 옳았다.

```sql
CREATE TABLE t_scale (g INT, v NUMERIC);
INSERT INTO t_scale VALUES (1, 9999999999999999999999999999999999999999);  -- 40자리
INSERT INTO t_scale VALUES (1, 1E-252);
SELECT SUM(v) FROM t_scale WHERE g = 1;
```

| | 결과 |
|---|---|
| 누계산 (수정 전) | `13503360588916997.76581908488507135536574` ← **에러 없는 쓰레기** |
| 이항 덧셈 (폴백) | `9999999999999999999999999999999999999999` |

40자리 값에 스케일차 252가 겹치면 292자리가 되는데 14워드는 270자리다. 밀려난 22자리가
소리 없이 사라졌다.

**왜 폴백은 멀쩡한가** — `float_numeric_*` 호출처가 저마다 시프트량을 묶고 있었기 때문이다:

| 호출자 | 보장 방식 |
|---|---|
| `add` / `sub` / `compare` | `result_prec = MAX(정수부) + result_scale`가 **정렬 후 크기 그 자체** |
| `db_value_div` / `db_value_mod` | 버퍼를 `lookup[exponent] + 19바이트`로 **시프트량에 비례** 할당 |
| `div_fast` | 고정 4워드지만 **스케일 항이 상쇄**된다: `exponent10 = 39 - (prec1-prec2) ≤ 57`, 19+57=76자리 < 77 |
| `normalize_for_hash` | 시프트를 `40 - precision`으로 **상한** (초과분은 버려도 되는 해시용) |
| **누산기 (우리)** | **고정 14워드 + 생 스케일차** ← 유일한 위반 |

`assert (carry == 0)`은 허술한 코드가 아니라 그 계약의 문서였고, 우리가 유일하게 어겼다.

**수정하다 두 번째로 틀린 것** — 값 확대 경로에서 `w`가 버퍼를 넘으면 거부하도록 바꿨는데,
그 `w`는 **상한 추정치**였다:

```c
w = val_used + (acc->scale - val_scale) / NUMERIC_DIGITS_PER_WORD + 1;
```

40자리 값(`val_used = 3`)에 스케일차 215면 `w = 15 > 14`라 거부되지만, 실제로는 255자리라
14워드에 **들어간다**. 그래서 `SUM`이 되던 그룹이 에러가 났다. 원래 코드의 클램프가 옳았고,
진짜 초과는 그다음 `mul_normalize`의 캐리가 정확히 잡는다. **상한은 클램프에만 쓰고 판정은
실측값으로 한다**(11번).

이 과잉거부는 처음 검증에서 통과했다 — 테스트 세트에 그 구간(스케일차 200~230)이 없었다.
`(100,215)` 같은 그룹 조합에서야 드러났고, 게이트 OFF와 대조해서 우리 탓임을 가렸다.

**남은 한계**: 수정 후에도 292자리 케이스는 **에러**다. 폴백은 계산해내므로, 게이트 ON에서
레거시보다 좁아진 셈이다. 밴드 테스트로 확인한 한계는 **269자리까지 정확, 270자리부터 에러**다.

**부작용 하나**: `mul_pow10`에서 `assert (carry == 0)`이 사라졌다. 누산기는 그 캐리를
정상적으로 검출해야 하는 유일한 호출자라 assert를 남길 수 없었는데, 그 결과 **나머지 7개
호출자의 계약을 debug에서 감시하던 장치가 없어졌다.** 되살리려면 각 호출처에서
`uint64_t lost = ...; assert (lost == 0); (void) lost;` 형태여야 한다 —
`assert (f () == 0)`은 NDEBUG에서 **호출 자체가 사라진다.**
