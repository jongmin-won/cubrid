## 1. 왜 하는가

| | 내용 |
|---|---|
| ① | **NUMERIC 덧셈 자체가 느렸다** — 별건으로 처리 (CBRD-27150, 일반 이항 연산자 최적화) |
| ② | **PG는 일반 이항 경로와 집계 누적 경로가 분리되어 있는데 CUBRID는 분리가 없다.** PG는 집계 시 `accum_sum_add`로 digit만 쌓고 정규화·저장형 변환을 그룹당 1회(`accum_sum_final`)만 한다. CUBRID는 집계가 **일반 이항 연산자를 행마다 호출**해서, 매 행 자릿수 계산·반올림 판정·17바이트 pack·DB_VALUE 재생성을 지불한다 |
| ③ | **그 결과 TPC-H Q1이 느리다** — 어느 구간이 얼마인지는 §2 |

즉 이 POC는 **CUBRID에 없던 "집계 전용 누적 경로"를 만드는 것**이다.

### 이항 연산자가 행마다 하는 일 (`float_numeric_db_value_add`의 단계 주석 그대로)

| 단계 | 집계에서 행마다 필요한가 |
|---|---|
| 1) 공통 precision/scale 계산 | scale 정렬 정보만 |
| 2) 작업 버퍼 크기 결정 | **불필요** — 누적기 크기는 고정 |
| 3) 계산 버퍼 초기화 + 절대값 패딩 | **불필요** |
| 4) scale 정렬 | 필요 |
| 5) 덧셈 | **필요 — 집계 누적에 실제로 필요한 것은 이것뿐** |
| 6) 결과 precision/scale 재계산 | **결과를 내보낼 때 1회면 충분** |
| 7) 반올림 + 17바이트 pack | 〃 |
| 8) DB_VALUE 저장 | 〃 |

집계는 중간 상태를 아무도 보지 않으므로 6·7·8은 그룹당 1회로 미룰 수 있는데, 행마다 지불하고 있었다.
perf 분해로 확인됨 — to-be의 누적 경로에는 **나눗셈·자릿수 계산·반올림·pack 심볼이 아예 없다**(as-is에서는 반올림 나눗셈 `__udivti3`가 누적 서브트리의 33.5%).
그리고 6·7·8을 미룬 결과가 §6의 "40자리 초과 SUM이 정답으로 바뀜"이다 — 행마다 반올림하지 않으므로 드리프트가 생기지 않는다.

## 2. TPC-H Q1 구간별 차이

같은 Q1을 세 단계로 잘라 차등 측정한다.

| 단계 | 쿼리 |
|---|---|
| **V0** | 스캔 + WHERE + GROUP BY + `COUNT(*)` — 집계 산술 없음 |
| **V1** | V0 + **단순 컬럼** 집계 5개 (`SUM/AVG(l_quantity)` 등) |
| **V2** | V1 + **집계 안에 수식**이 있는 것 2개 (`SUM(ep×(1−disc))`, `SUM(ep×(1−disc)×(1+tax))`) = 풀 Q1 |

**병렬 6워커, 데이터 버퍼 8G, 6,000만 행, 3회 최솟값** — 이 구간별 표는 **SA 모드**에서 잰 것이다.
CS 모드 전체 수치는 §5에 있고(as-is 30.56s → to-be 14.87s), 개선율은 두 모드가 사실상 같다.
구간별 재측정은 하지 않았다 — CS 모드 결함 조사에 시간을 썼고, 구간 비율이 달라질 이유가 없다.

| 구간 | as-is | **to-be** | 개선 | 이 구간의 비용 정체 |
|---|---|---|---|---|
| **V0** | 6.16s | 6.03s | — | 스캔·deform·해시 그룹핑 — **NUMERIC 무관** |
| **V1−V0** | +13.09s | **+5.71s** | **−56%** | 누적 그 자체 + 인자 운반 |
| **V2−V1** | +11.80s | **+3.34s** | **−72%** | 집계 안 수식의 연산·중간 DB_VALUE |
| **V2 = Q1** | **32.91s** | **15.03s** | **−54%** | |

PG(동일 장비, 병렬 6워커) **10.3s** → 격차 as-is 3.0x → **to-be 1.46x**

**읽는 법**: 개선분은 전부 V1·V2 구간에서 나왔고 V0은 그대로다. 즉 **NUMERIC 집계 경로만 바뀌었고 스캔·그룹핑은 손대지 않았다.** 남은 격차의 최대 항목은 V0의 PG 대비 2.2x(스캔·deform, NUMERIC 무관 영역)다.

## 3. NUMERIC 연산 함수의 종류와 역할

NUMERIC 연산자는 **소유 구간이 나뉘어 있다.** 이 POC는 그중 **집계 구간만** 확장하고
나머지는 손대지 않는다 — 어느 함수군이 무엇을 담당하는지 알고 나면 §4의 변경 내역이 읽힌다.

| 구간 | 담당 함수군 | 이 POC와의 관계 | 예시 |
|---|---|---|---|
| 단순·특수 (serial 등) | `numeric_db_value_*` | 그대로 — 워드 변환이 오히려 오버헤드다 | SELECT s.NEXT_VALUE |
| **일반 이항 연산** | `float_numeric_db_value_*` | **손대지 않음** — CBRD-27150이 최적화한 구간 | SELECT col1 + 3 |
| **집계·분석 누적** | 누계산(`numeric_sum_acc_*`) + 집계 내부식 혼합(`numeric_poc_chain_*`) | **이 POC가 신설·확장** | SELECT SUM(col1), AVG(col1), SUM(col1 * col2) |

**경계를 어떻게 지키는가** — 구분은 실행 시점에 결정된다. 집계 인자로만 소비되는 출력 수식을
쿼리 시작 시 1회 표시해 두고(`REGU_VARIABLE_AGG_OPERAND`), **표시된 것만** 혼합한다.
판정 근거는 *집계 인자가 그 수식이 쓴 DB_VALUE를 그대로 가리킨다*는 것이다(포인터 일치, gdb 실증).

경계가 지켜졌음을 측정으로 확인했다 — 순수 이항 연산(`WHERE ep×disc`)은 게이트 off와 동일하다
(4.25s vs 4.08s). 즉 일반 이항 연산 경로는 이 POC의 영향을 받지 않는다.

### 각 항목 상세

#### 누계산 (워드 누산기)

집계는 중간 상태를 아무도 보지 않는다. 그런데 기존 경로는 일반 이항 연산자를 행마다 호출해
**결과 precision/scale 재계산 → 반올림 → 17바이트 pack → DB_VALUE 저장**을 매번 지불했다(§1의 6·7·8단계).
누계산은 값을 `uint64` 14워드(254자리)에 scale만 맞춰 더해 두고, 그룹이 끝날 때 한 번만
반올림·패킹한다. 40자리를 넘어도 계속 쌓기 때문에 **행마다 반올림하며 생기던 드리프트가 사라진다**
— §6의 "40자리 초과 SUM이 정답으로 바뀜"이 이것이다. 254자리를 넘으면 폴백이 아니라
`ER_IT_DATA_OVERFLOW`다.

#### 인자 peek

집계 인자를 읽을 때 `fetch_copy_dbval`은 DB_VALUE를 새로 만들어 값을 복사하고 나중에 해제한다.
누적은 값을 읽기만 하므로 `fetch_peek_dbval`로 **포인터만 받으면** 된다. 집계·분석 양쪽에 적용했고,
분석은 누산기가 이미 돌고 있을 때만 peek하고 첫 값·NULL·비NUMERIC은 기존 경로를 그대로 쓴다.

#### 직결 디스패치 / 워드 폭 산출

누계산이 활성인 동안에는 함수 종류(SUM/AVG/기타)를 다시 판정할 필요가 없어 분기를 건너뛴다.
워드 폭은 값의 상위 워드를 스캔해 구하던 것을, NUMERIC 헤더의 precision이 자릿수의 상한이라는
성질을 이용해 룩업 한 번으로 바꿨다.

#### 집계 내부식 혼합 (워드 체인)

`SUM(ep × (1 − disc) × (1 + tax))`처럼 집계 인자가 수식이면, 기존에는 연산마다 NUMERIC DB_VALUE를
만들고 버렸다. 혼합은 그 수식을 `{uint128 계수, scale, 부호}` 하나로 들고 다니며 `+`,`−`,`×`를
정수 연산으로 처리하고, **마지막에 DB_VALUE 하나만** 만든다. 중간 DB_VALUE가 0개가 된다.

어느 수식이 대상인지(적용 범위)는 §3에, 어떤 조건에서 폴백하는지는 아래 절에 있다.

#### 누계산 공유

`SUM(x)`와 `AVG(x)`가 같은 인자를 받으면 쌓는 합이 같다. 그래서 먼저 나온 쪽만 누적하고,
뒤쪽은 값을 만들 때(materialize) 누산기 상태를 복사해 각자 마무리한다. AVG가 먼저 값을 만들면
합이 평균으로 바뀌므로, **복사는 반드시 materialize 전에** 일어나야 한다.

**공유 관계 저장 규칙 — `shared_from`**

집계 노드마다 "내 누산을 앞선 몇 번째 집계와 공유하는가"를 정수 하나(`shared_from`)로 들고 있다.
규칙은 세 개다.

| | 규칙 |
|---|---|
| **초기화** | `0` = 공유 없음 (본인이 직접 누적) |
| **저장** | 공유할 앞선 집계의 인덱스 **+ 1** |
| **사용** | 값 **− 1** 로 되돌려 인덱스로 쓴다 |

Q1의 집계 8개에 실제로 담기는 값:

| # | 집계 | `shared_from` | 뜻 |
|---|---|---|---|
| 0 | `SUM(qty)` | `0` | 본인이 누적 |
| 1 | `SUM(ep)` | `0` | 〃 |
| 2 | `SUM(ep×(1−disc))` | `0` | 〃 |
| 3 | `SUM(ep×(1−disc)×(1+tax))` | `0` | 〃 |
| 4 | `AVG(qty)` | **`1`** | 0번 `SUM(qty)`의 누산을 공유 |
| 5 | `AVG(ep)` | **`2`** | 1번 `SUM(ep)`의 누산을 공유 |
| 6 | `AVG(disc)` | `0` | 같은 인자의 SUM이 없어 공유 상대가 없다 |
| 7 | `COUNT(*)` | `0` | 누계산 대상이 아니다 |

```c
agg_p->accumulator.shared_from = owner_index + 1;            /* 저장: +1 */
...
if (agg_p->accumulator.shared_from <= 0)  continue;          /* 0 = 공유 없음 */
owner_p = qdata_agg_node_at (agg_list, shared_from - 1);      /* 사용: −1 */
```

`<= 0`으로 음수까지 걸러내는 것은 **방어 코드**다. 정상 흐름에서 음수는 나올 수 없지만
배열 인덱스로 쓰는 값이므로 상한만이 아니라 하한도 검사한다(§9 4번).

**`0`을 "없음"으로 정한 이유**는 하나다 — 실행 전용 필드는 0으로 채워진 채 시작할 수 있고,
그 상태가 곧 "공유 없음"이면 초기화가 닿지 않은 경로에서도 오동작하지 않는다.
단 그 전제는 **스트림 경로에서 성립하지 않았다**(`stx_alloc_struct ()`는 memset을 하지 않는다 —
§9 함정 7). 그래서 최종 형태는 *`0` = 없음으로 두고, 스트림 복원 지점에서 명시적으로도 초기화한다*다.

#### 분석 함수 확장

집계는 그룹이 끝날 때 한 번만 값을 내지만, 누적 분석 함수(`SUM(x) OVER (ORDER BY ...)`)는
**행마다 그때까지의 합**을 내보내고 계속 쌓아야 한다. 그래서 누산기를 끝내는 `finalize`와 별도로,
누산기를 그대로 남긴 채 값만 뽑는 `snapshot`을 두었다.

#### 서버 모드 결함 수정 (성능 아님 — 기능 복구)

**증상**: CS 모드(`csql -u dba <db>`)에서 NUMERIC 집계가 `Query execution failure #NNNNN`으로 실패했다.
게이트 on/off 모두, 직렬·병렬 모두. SA 모드에서는 정상이었다.

**원인**: 서버 모드는 클라이언트가 XASL을 **직렬화해 서버로 보내고**, 서버가
`stx_build_aggregate_type ()`으로 다시 만든다. 그런데 `stx_alloc_struct ()`는 `db_private_alloc`만
하고 **memset을 하지 않는다.** 스트림에 실려오지 않는 실행 전용 필드(`shared_from`, `num_sum_acc`)는
그 메모리에 있던 값을 그대로 갖게 되고, 쓰레기 인덱스로 owner를 찾지 못한 전파 코드가
**`er_set` 없이** `ER_FAILED`를 반환했다 — 그래서 에러 메시지가 저렇게 무의미했다.

**수정 세 가지** (`30305dcff`):

| | 내용 |
|---|---|
| 스트림 복원 지점 초기화 | `clear_value_at_clone_decache = false` 옆에서 `shared_from = 0`, `num_sum_acc.is_active = false`를 명시 |
| 전파를 게이트 안으로 | 게이트 off에서는 아무것도 링크되지 않으므로 전파 자체를 건너뛴다 (§9 함정 5의 재발이었다) |
| 실패에 에러 설정 | owner를 못 찾으면 `ER_QPROC_INVALID_XASLNODE` — 다음에는 진단이 가능하도록 |

**왜 여태 못 봤나**: SA 모드는 XASL을 메모리로 공유해 스트림 경로를 아예 타지 않는다.
POC 전체를 SA로만 측정·검증했기 때문에 드러나지 않았다. 자세한 경위는 §9 함정 7.

#### 기각: 해시 델타 스킵 (`5bec86046` 되돌림)

해시 집계는 스필 한도를 지키려고 행마다 누산기 메모리 증감을 다시 계산한다. 누산기 크기가
고정이면 그 증감은 항상 0이므로 건너뛰려 했다.

**기각 사유** — 판정 조건이 `pr_is_variable_type()`이었는데, CUBRID는 **NUMERIC을 가변 타입으로
분류**한다. 즉 NUMERIC 집계에서는 조건이 절대 성립하지 않아 **처음부터 한 번도 동작하지 않았다.**
그동안의 모든 성능 수치는 이 최적화 없이 나온 값이고, 되돌려도 회귀가 없다(병렬 Q1 14.7s 유지).

여기서 헷갈리기 쉬운 점: DB_VALUE 안의 NUMERIC은 `DB_NUMERIC_BUF_SIZE`(**17바이트**) **고정 버퍼**다.
그런데 회계에 쓰는 `pr_value_mem_size ()`는 그 버퍼 크기가 아니라 **값의 논리 크기**를 돌려준다 —
`mr_data_lengthval_numeric ()`이 `disk` 인자를 무시하고 float numeric은 precision 룩업,
fixed numeric은 유효 바이트 수로 계산한다. 그래서 값이 커지면 회계값도 커진다.
(부수적으로 알게 된 것: 해시 메모리 회계는 실제 점유(17바이트 고정)와 다른 값을 센다 — 기존 엔진
설계이고 POC 범위 밖이지만, 재도전 조건인 "도메인 상한 회계"가 더 타당해지는 근거다.)
조건을 "누계산 대상 SUM/AVG + COUNT"로 바꾸면 발동하지만, 폴백이 일어나면 `accumulator.value`가
갱신되어 증감이 0이라는 보장이 깨지고 **스필 회계가 부정확**해진다(결과는 맞지만 메모리 초과 위험).
안전하게 하려면 도메인 상한 기반 회계를 새로 도입해야 하는데, 효과는 워커 CPU 4.3%이고
**병렬 wall로는 노이즈에 묻혀 측정되지 않았다**(min 14.87 → 14.59s, median 동일).
효과 대비 위험·복잡도가 맞지 않아 전량 되돌렸다.

**재도전 조건**: 스필 회계를 "값 실측"에서 "도메인 상한"으로 바꾸는 작업과 함께. 그때는 폴백 여부와
무관하게 상한이 고정이므로 행마다 재계산할 이유가 사라진다.

### 폴백 조건 — 두 종류로 나뉜다

**구조 조건 (쿼리 단위)** — 걸리면 그 수식은 처음부터 끝까지 혼합을 쓰지 않는다.

| 조건 | 예 |
|---|---|
| 집계 인자로 소비되는 수식이 아님 | `SELECT a*b`, `WHERE a*b > 0` |
| `+`, `−`, `×` 외의 연산이 트리에 섞임 | **나눗셈**, 함수 호출, CAST |
| 리프가 단순 값 참조가 아님 | 서브쿼리, 함수 결과 |
| 트리 깊이가 `max_recursion_sql_depth`에 근접 | 극히 깊은 수식 |
| 결과 도메인이 NULL 타입 | |
| 게이트 off | |

**값 조건 (행 단위)** — **행마다 독립적으로 판정**한다. 1행은 혼합, 2행은 폴백, 3행은 다시 혼합이 될 수 있다.

| 조건 | 언제 |
|---|---|
| 리프가 NULL | |
| 리프가 NUMERIC이 아님 | 정수·문자열이 섞인 수식 (`a*2`) |
| 리프 계수가 **128비트 초과** | 39자리를 넘는 값 |
| 중간·최종 계수가 128비트 오버플로 | 곱셈으로 커진 경우 |
| 곱셈 결과 scale > **252** | 레거시는 에러가 아니라 **반올림**해서 252로 맞춘다 — 체인이 재현 불가 |
| 곱셈 결과 scale < **−214** | 레거시는 **`ER_IT_DATA_OVERFLOW`**(WARNING) + 결과 NULL — 체인이 값을 내면 동작이 달라진다 |
| 두 항의 scale 차이가 38 초과 | 정렬에 `10^39` 이상이 필요 |

어느 쪽을 타도 **결과는 비트 단위로 같다.** 128비트에 들어가는 값은 최대 39자리이므로 기존 연산자가 반올림하는 경계(40자리)에 닿지 않기 때문이다. 즉 폴백은 **성능만** 되돌리고 답은 바꾸지 않는다 — Q1은 수식 값이 15자리 안쪽이라 사실상 전 행이 혼합을 탄다.

병렬 전용이라 직렬로는 재현되지 않고 병렬 wall로는 0.43s가 노이즈에 묻힌다 → 별도 이슈 후보.

## 8. 본구현 이관 과제

`design_numeric_sum_accumulator.md` 체크리스트 참조. 핵심 4건:

1. 병렬 XASL 경로 — 출력 일치는 실검증 완료. **워커는 자기 XASL을 쓰므로 직렬 쪽 준비 코드가 닿지 않는다**(이 POC에서 실측으로 확인)
2. 해시 스필 시 finalize 폴백의 반올림 1회 추가 — 불변식 논의
3. 게이트 제거 (환경변수는 측정용)
4. **결과 변화 합의** — 40자리 초과 SUM이 정답으로 바뀜 → 스펙 합의 + QA answer 갱신

## 9. 환경 · 함정

- 병렬은 `/*+ PARALLEL(n) */` 힌트 필수 (heap 자동 병렬 없음, `parallelism`은 동적 변경 불가)
- 벤치 DB를 **`demodb`에 두지 말 것** — 빌드가 초기화한다. `pocbench`(디스크) 사용
- 빌드/install이 `cubrid.conf`·`databases.txt`를 초기화 → 측정 전 복원 + **버퍼 크기 재확인**
- **`build.sh install`이 실행 트리를 갱신하지 않는다** — `build_x86_64_release/_install/CUBRID`에만
  설치되고 `$CUBRID`(`/home/cubrid/CUBRID`)는 그대로일 수 있다(로그가 전부 `Up-to-date`, exit=0).
  `cp -a _install/CUBRID/bin/. $CUBRID/bin/` + 같은 식으로 `lib/`를 복사한다(conf는 제외).
  **검증 전에 `ls -l $CUBRID/bin/cub_server`로 타임스탬프를 확인할 것** — 이걸 놓쳐서 진단 로그를
  넣은 빌드 2회가 반영되지 않았고, "로그가 안 찍힌다 → 이 경로가 원인이 아니다"라는 잘못된
  추론을 두 번 했다
- 데이터 버퍼 512M ↔ 8G는 Q1에 무영향
- `cubrid server start`를 파이프에 물리면 데몬이 FD를 상속해 블록 → `>/dev/null`
- loaddb 날짜값은 따옴표 필수 (`'1992-01-02'`)
- **프로파일의 CPU %를 wall 개선으로 착각하지 말 것** — 6워커 병렬에서 워커 CPU 합은 wall의 약 5.8배다.
  즉 **CPU 1s 절감 ≈ wall 0.17s**. 병렬 Q1의 측정 노이즈가 ±1.5s이므로 **CPU 4% 미만의 개선은 병렬 wall로
  검증할 수 없다** — 그런 항목은 `PARALLEL` 힌트를 뺀 직렬로 재야 CPU 절감이 1:1로 드러난다

### 집계 코드를 건드릴 때 (이번에 값비싸게 배운 것)

집계는 경로가 **직렬 / 병렬 / 해시 / 정렬 / buildvalue**로 갈리고, 집계 리스트도 3중이다:

```
xasl->proc.buildlist.g_agg_list   원본 — 쿼리 시작 시 준비
gbstate->g_dim[N].d_agg_list      GROUP BY 차원별 — finalize가 이걸 쓴다
value->accumulators[]             해시 그룹별 배열 — 위 둘을 잇는다
```

그래서 새 처리를 넣을 때 다음을 전부 확인해야 한다. 이번에 이 유형의 결함이 **7번** 나왔다.

1. **병렬 경로에도 넣었는가** — 워커는 자기 XASL을 쓰고, 도메인 해소조차 전용 함수(`..._for_parallel_heap_scan_g_agg`)가 따로 있다. 직렬 쪽만 고치면 병렬에서 조용히 무효가 된다.
   **교훈을 배운 뒤에는 이전 커밋도 소급 점검할 것** — 이 함정을 알기 전에 만든 `fixed_hvalue_size`(`5bec86046`)를
   다시 보지 않아서, 그것이 병렬에서 안 도는 줄 알고 하루 뒤에 고치려 했다. 실제 원인은 병렬이 아니라
   타입 분류였고(§4 기각 항목), 결국 전량 되돌렸다. **"쿼리당 1회 판정"을 새로 만들면 그 즉시 병렬 호출
   지점을 함께 만들고, 이미 만든 것들도 같은 눈으로 훑어야 한다.**
2. **값을 꺼내는 지점을 모두 찾았는가** — 최종 출력 / 해시 스필 / 부분합 병합
3. **새 필드의 센티넬이 `0`인가** — 실행 전용 필드는 직렬화되지 않아 0으로 채워지고, 초기화 함수가 모든 경로에서 호출된다는 보장이 없다. `-1`을 "없음"으로 쓰면 초기화 누락이 곧 오동작이 된다. 인덱스는 1-based로 저장해서 `0 = 없음`이 되게 한다
4. **음수·범위 방어** — 배열 인덱스로 쓰는 값은 상한만이 아니라 **하한도** 검사한다
5. **게이트 안에 있는가** — off에서 기존 동작이 100% 유지되어야 한다
6. **SA(직렬)로만 gdb 확인하지 말 것** — 병렬 특유 문제가 드러나지 않는다
7. **SA 모드로만 측정·검증하지 말 것** — 서버 모드(CS)는 클라이언트가 XASL을 **직렬화해서 서버로 보내고**, 서버는 `stx_build_aggregate_type ()`으로 다시 만든다. SA는 XASL을 메모리로 공유해 이 경로를 아예 타지 않는다

#### 7번이 실제로 터진 방식 (커밋 `30305dcff`)

`stx_alloc_struct ()`는 `db_private_alloc`만 하고 **memset을 하지 않는다.** 그래서 스트림에서
복원된 accumulator의 실행 전용 필드(`shared_from`, `num_sum_acc`)는 그 메모리에 있던 값을
그대로 갖는다. 즉 **3번의 "0으로 채워진다"는 전제가 스트림 XASL에서는 성립하지 않는다** —
`shared_from` 주석에 "스트림에서 온 XASL이 그 예"라고 적었던 것이 정확히 거꾸로였다.

쓰레기 인덱스로 `qdata_propagate_shared_accumulators ()`가 owner를 찾지 못하고,
`er_set` 없이 `ER_FAILED`를 반환해 `Query execution failure #NNNNN`이라는 진단 불가능한
메시지만 남았다. 게다가 그 함수는 **게이트 밖**에서 돌고 있었다(5번 재발).

증상이 게이트·집계 개수·통계 유무에 따라 성공/실패로 갈려 오래 헤맸다 — 초기화되지 않은
메모리의 전형이다. 수정은 `clear_value_at_clone_decache = false` 옆에 두 필드를 명시적으로
초기화하고, 전파를 게이트 안으로 옮기고, owner 실패에 에러를 설정하는 것이다.

**검증은 반드시 서버 모드(`csql -u dba <db>`)로 한다.** `csql -S`는 SA 모드다.
게이트는 환경변수 `CUBRID_NUMSUM_ACC=1`을 **서버 프로세스가** 가져야 켜지므로,
서버 모드 A/B는 `cubrid server stop` → 환경변수 설정/해제 → `start`로 전환한다
(`/proc/<cub_server pid>/environ`으로 실제 적용을 확인할 것).
